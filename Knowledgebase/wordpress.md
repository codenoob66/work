# WordPress Knowledge Base

## General Procedures & Policies

### 1. WordPress Disk Space and wp-content Management
- **Scenario:** WordPress websites can consume massive amounts of disk space over time. The main content of a WordPress site (themes, plugins, uploads, cache, and media files) resides in the `wp-content` directory inside the public webroot (`httpd.www/wp-content`).
- **Diagnosis:**
  - Check `wp-content/uploads` for unoptimized images or backup archives.
  - Check `wp-content/cache` for heavy caching plugin files.
  - Ensure security logs or debug logs (e.g., `debug.log`) are not growing unchecked.
- **Resolution Steps:**
  1. Identify which sub-folder inside `wp-content` is consuming the most disk space.
  2. Advise the customer to optimize images, delete unused plugins/themes, and configure caching/backup plugins to store files externally or limit retention.
  3. Ensure that the root directory `tmp` folder (which may store PHP/session files generated by WordPress) is also checked and cleared if needed.

### 2. WordPress 1-Click Installation & Troubleshooting
- **Policies:**
  - one.com offers a 1-Click WordPress installer in the Control Panel for supported hosting plans.
  - For manual migrations, database connection details must match the configured database inside `wp-config.php` (DB_NAME, DB_USER, DB_PASSWORD, DB_HOST).
  - Common white screen of death (WSOD) errors can often be resolved by temporarily disabling all plugins (renaming the `wp-content/plugins` folder) or enabling PHP error reporting.

### 3. Deactivate WordPress Plugins via phpMyAdmin
- **Source:** [Deactivate WordPress plugins in phpMyAdmin](https://help.one.com/hc/en-us/articles/115005593985-Deactivate-WordPress-plugins-in-phpMyAdmin) (last updated March 18, 2025)
- **Scenario:** A plugin breaks the WordPress site and the customer cannot log in to deactivate it from the dashboard. All plugins can be deactivated via phpMyAdmin without logging into WordPress.
- **Resolution Steps:**
  1. Open phpMyAdmin (see also: [How do I open and use phpMyAdmin?](https://help.one.com/hc/en-us/articles/115005585909)).
  2. Select the WordPress database in the left menu (often matches the domain, e.g. `onecom_domain_com`).
  3. Open the options table: `wp_options` (or `wp_XXXX_options` for multisite).
  4. Click **Search** and set:
     - Column: `option_name`
     - Operator: `=`
     - Value: `active_plugins`
     Then click **Go**.
  5. Click **Edit** on the result row.
  6. Clear the entire **option_value** field (leave it empty) and click **Go**.
- **Result:** All plugins are deactivated. The customer can log back into WordPress and reactivate plugins one by one to identify the problematic plugin.
- **Related help articles:**
  - Fix the WordPress White Screen of Death
  - Restore a backup of your web space
  - How do I open and use phpMyAdmin?
  - How do I open and use File Manager?
  - Guide: How to use phpMyAdmin
- **Note:** An alternative (file-based) method is renaming `wp-content/plugins` via File Manager — see procedure 2 above.

### Case Study 2: Severe TTFB on Large WP Sites (wp_postmeta Index)
- **Ticket Reference:** Conversation with Richard (carpsocial.com)
- **Domain:** `carpsocial.com`
- **Context:** Customer experienced severe TTFB delays (20-50 seconds) on a large WordPress site, making it unusable. The issue reappeared after every backup restore or staging site deployment.
- **Diagnosis:** The root cause was identified as inefficient MySQL queries on the `wp_postmeta` table, specifically when ordering by `meta_id`. This is a known bottleneck on the shared hosting platform for WordPress sites with very large `wp_postmeta` tables. Restoring a backup or deploying a staging site was overwriting the manual database optimizations applied by engineers.
- **Resolution (Permanent):** To provide the customer with a self-service, permanent solution, they were given the direct SQL command to create the necessary compound index. They are instructed to run this command via a database tool (e.g., phpMyAdmin) after any restore/deployment to prevent the issue from recurring.
- **SQL Command to provide:**
  ```sql
  CREATE INDEX idx_postid_metaid_metakey ON wp_postmeta (post_id, meta_id, meta_key);
  ```

### Case Study 6: WordPress Theme Loading Failure Due to External CDN (GSAP) Dependency
- **Ticket Reference:** Takeaway 39 (Shared with Hosting)
- **Customer Name:** Courcey (Ziggy)
- **Customer Email:** ziggy001@me.com
- **Domain:** ziggysentertainmentgroup.com
- **Context:** WordPress site stuck on a spinning cross preloader animation after hosting plan upgrade. The theme's preloader relies on GSAP (gsap.min.js, ScrollTrigger.min.js) and Font Awesome loaded from cdnjs.cloudflare.com. These external CDN requests were failing silently from the UK, so the preloader never animated out. Engineers confirmed the hosting upgrade was not the cause — the CDN was simply unreachable from the customer's region. Fix: download GSAP and Font Awesome assets locally to the server (e.g., /wp-content/themes/... or a local JS folder) and enqueue them locally. Key lesson: WordPress themes that depend on external CDN-hosted JavaScript libraries are vulnerable to region-specific loading failures. When a site works in some regions but not others, check external script dependencies first.

### Case Study 7: Contact Form 7 Email Failure Due to PHP Mail Disabled (SMTP Fix)
- **Ticket Reference:** Takeaway 44 (Shared with Email)
- **Customer Name:** Sebastian
- **Customer Email:** sebastian@everday.se
- **Domain:** meraresurs.se
- **Context:** Customer reported Contact Form 7 emails not sending on https://www.meraresurs.se/kontakt/. Error captured via WP Mail SMTP plugin: "Could not instantiate mail function." The site was using the default PHP mail() function, which is disabled on the hosting. The customer's custom MX records were initially flagged by the automated support but were not the actual cause — MX records affect receiving, not sending. Escalated to 2nd level, who confirmed the fix: (1) create the desired sender email account (e.g. wordpress@meraresurs.se) in CP > Email, and (2) configure WP Mail SMTP to use one.com's SMTP server with those credentials instead of the default PHP mail function. Key lesson: when "Could not instantiate mail function" appears on one.com hosting, PHP mail is blocked — the customer must use SMTP via an email account configured in the Control Panel. Guide: https://help.one.com/hc/en-us/articles/6949620532113-How-to-send-emails-in-WordPress-using-the-WP-SMTP-Mail-plugin

### Case Study 9: Never Recommend Backup Plugins — Use Backup & Restore or Manual Backup
- **Ticket Reference:** Takeaway 48 (Shared with Hosting)
- **Customer Name:** Roya
- **Customer Email:** roya.phat@qrut.se
- **Domain:** qrut.se
- **Context:** Customer asked on chat which plugin to recommend for a full-scale WordPress backup, later clarifying she only needed the database backed up. A draft response recommended third-party backup plugins (UpdraftPlus, WP-DB-Backup) — this contradicts one.com's "Discouraged WordPress plugins" policy and was caught before sending. Policy: one.com advises against backup plugins in general because they are resource-heavy, cause high server load and performance issues, and can pose security risks. Correct guidance for any backup request: (1) use the Backup & Restore add-on product (Control Panel → Hosting) to save and restore the database and website, (2) alternatively create a manual backup — database export via phpMyAdmin (Export option) and/or file backup of the web space, and (3) mention that one.com takes security backups every night as an extra safety net. Key lesson: never recommend backup plugins to one.com customers, even popular ones — always check the Discouraged WordPress plugins list before recommending any plugin, and steer backup questions to Backup & Restore or manual backups instead.

### Case Study 10: WooCommerce Thank-You Page HTTP 500 Caused by OOM Kills (Shared with Hosting)
- **Ticket Reference:** Takeaway 49 (Shared with Hosting)
- **Customer Name:** Patrick
- **Customer Email:** patrick@pokedrop.dk
- **Domain:** pokedrop.dk
- **Context:** On pokedrop.dk (WooCommerce), order #3404 was created successfully and the confirmation email went out, but the customer received an HTTP 500 instead of the order received/thank-you page on 30 September 2026 at ~16:27–16:30 CEST (14:27–14:30 UTC). No historical PHP error was visible in WooCommerce logs or File Manager. 2nd level reviewed server logs for that window and found multiple OOM kills of php-cgi-8.3 processes on the account — the PHP process handling the thank-you page was terminated mid-request for exceeding available memory, which is also why no plugin stack trace was recorded. Account was on the Explorer package; guidance given was to optimise the site (lean plugin set, keep WooCommerce/theme updated, avoid stacking heavy plugins) or upgrade the hosting package. Key lessons: (1) successful order + failed thank-you page + no PHP error log for that request is a classic OOM signature on shared hosting, not a checkout logic bug. (2) An OOM kill produces no stack trace — do not promise the customer a specific plugin as the root cause. (3) WooCommerce checkout/order-received flows are memory-intensive; on smaller packages (e.g. Explorer) optimisation or a resource upgrade is the correct remediation.

### Case Study 12: wp-admin Login Failed After Plaintext Password Save in phpMyAdmin (MD5 Required)
- **Ticket Reference:** Takeaway 54
- **Customer Name:** N/A
- **Customer Email:** copenhagennailartist@gmail.com
- **Domain:** claircopenhagen.dk
- **Context:** Customer could not log in to claircopenhagen.dk/wp-admin, first getting Danish error for no account with that username or email, then after DB edit getting password incorrect for copenhagennailartist@gmail.com. Investigation in phpMyAdmin showed wp_users contained only ID 1 admin and ID 2 svc_ system user, so customer email was not present. Fix was to Edit ID 1 admin, replace user_email with customer email and set new user_pass. Customer screenshots showed user_pass saved as plaintext Targosz24 with Function column blank and saved after being told this is fine. WordPress rejects plaintext and requires MD5 selection in Function column for user_pass, or SQL alternative UPDATE wp_users SET user_pass = MD5('NEW-PASSWORD') WHERE ID = 1. Lesson: never approve save without MD5 selected, explicitly guide to Function dropdown in same user_pass row before Go, warn not to delete svc_ user and not to share passwords, and treat exposed plaintext password as must-change. Secondary theme-disappeared issue remained pending after access restore.
